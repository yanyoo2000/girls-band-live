# critic-feasibility 的评审意见

> 阅读范围：`docs/brief.md`、`docs/templates/critic-review.md`、`docs/production-plan.md`、`docs/reports/m2-discussion.md`、`docs/concepts/hybrid-{a,b,c}.md`、`lineage.md`、`comparison.md`；10 份互评经 M2 门禁报告覆盖，未逐篇读原文；未读 archive。
> 口径：React 19 + TS strict + Three.js 0.186 + Vite 单文件（`file://` 可玩、≤4MB、目标 ≤2MB）、零外部素材、WebGL2、仅桌面键鼠、7 名工程师、60fps@1280×720。按修订 rubric（Fun 30 / Theme 20 / Originality 20 / Depth 10 / Polish 10 / Feasibility 5 / Scope 5）：可行性只问"有没有可信路径"，不用否决权。
> 结论：三案都存在可信路径；A advance（low）／B advance（high，不构成否决）／C advance（medium）。

## 总览

A 想成为一台 6:30 的街机：一张 16 步表同时驱动声音、刷怪与判定，张力全压在"按住—松手"那八帧。B 想把舞台本身变成乐器：六根弦、向下成长、只有一把程序化吉他发声。C 想把观众当弹药与血条。三案都满足零素材、程序化音频、实例化人群、单文件构建。差别在风险形状：A 押一个可分离的手感时刻，B 押两个不可砍的技术赌注，C 摊成八个小系统的集成质量。按新权重可行性只值 5%，只回答路在哪。

## Hybrid A（稳妥/可行性优先）

- 一句话判断：风险最集中、也最易局部验证的一案——那两秒手感成立，其余都是可预算的量。
- 三个优点：
  1. 16 步表是单一数据源：音频、刷怪、判定、灯光共享一份 pattern，四个模块只剩"读表 + 触发器"。
  2. 人潮是四标量 + 局部扰动，不需要寻路、刚体、每实体状态机；1000 人一个 InstancedMesh。
  3. 音频可降级为底鼓 + 节拍器而不塌；6:30 一局让 QA 每小时跑 4–5 局。
- 三个红旗：
  1. 16 盏真 SpotLight 叠 MeshStandardMaterial 会触发多光源开销，再叠 1000 人潮可能掉到 40fps；应假光化：加法锥体 + 少量方向光。
  2. 判定跟 AudioContext 时钟、鼓棒动画跟 rAF，两条时钟不接线就会出现"画面上到顶、判定说没到"；±0.12s 窗在 60Hz 下只有 7 帧。
  3. 人潮若按每实体邻域查询实现，CPU 先于 GPU 崩；每帧全量上传 1000 个矩阵同样吃预算。
- 三个必须回答的问题：
  1. 人潮是"64×64 密度场 + 实例渲染"还是逐实体模拟？请给每帧 sim ≤4ms 的预算。
  2. 鼓棒判定与音频时钟怎么桥接？谁签"静音可玩 + 砸准 70%"？
  3. 改成 8 假灯后，"3 帧内 16 盏灯全亮过曝"还成立吗？
- Verdict：advance　｜　风险等级：low（密度场、假光化、单一音频时钟任一不成立则升 medium）
- 收敛路径：16 灯→8 假灯；6 编曲→4；4 行为 + 2 精英→3 行为；Boss 3→2 阶段。M5 第一周只做"一主唱 + 一空场 + 3 次砸 + 一条 8 小节 loop"。

## Hybrid B（主题/原创优先）

- 一句话判断：唯一"主题与实现同一处承重"的方案——弦的手感与吉他音色不是打磨项，是立项条件；两件事都有确定路。
- 三个优点：
  1. 几何便宜：六根管状体（约 6k 顶点）每帧重算也比更新 1000 个实例矩阵轻，顶点位移即可，不需要物理引擎。
  2. 人群分两层：冲台实例 + 坐席静态实例，坐下的人退出模拟只留位置与颜色；灰→彩只是 instanceColor 插值。
  3. 无卡池、无升级菜单，progression 模块几乎清零。
- 三个红旗：
  1. Karplus-Strong 要逐样本处理；AudioWorklet 在 `file://` 下有 origin 限制，Vite 单文件未必兜住，必须先实测。
  2. 手感不可砍：踩—放要有重量与回弹，还要 V 沿弦滑动、人潮钻弦缝；砍到三弦仍要手感。
  3. 范围最大：4 角色、6 弦、Boss 3 阶段、断弦地形、调弦、独奏、500 人一声"啊"，M6 最易"每样都有、每样不够"。
- 三个必须回答的问题：
  1. 30 秒闭眼听谁来做、什么标准算过？若 worklet 不可靠，是否接受启动时预渲染 6 个音色缓冲区？给出内存上限。
  2. "断 1–3 根"与"六→五→三→一"在 M4 前怎么统一？断弦数决定地形与装弦 UI。
  3. 10–12 分钟一局、QA 每小时只能跑 2–3 局：是否接受压到 8 分钟？
- Verdict：advance　｜　风险等级：high（只用于排期与切片顺序）
- 收敛路径：4 角色→2；6 弦→4 弦（4→3→2→1 仍成立）；4 动作→3；敌人行为→1 + 精英；Boss 3→2；500 人"啊"→8 声部池。先交两个切片。

## Hybrid C（乐趣/循环优先）

- 一句话判断：系统最多、单件最便宜的一案——性能不是瓶颈，集成与因果可读才是。
- 三个优点：
  1. 28×36 座位网格是天然加速结构：光与观众的交集是桶查询 O(格子数)，1008 座一个 InstancedMesh，热度写 Float32Array。
  2. 观众用 MeshBasic/顶点色自发光即可，绕开"1000 物体 + 多光源"陷阱；噪音走对象池；合唱用 8–12 声部池映射千人。
  3. MVP 能缩到"一束光 + 两排人 + 三种噪音"，两周可出切片。
- 三个红旗：
  1. "白光吃掉颜色＝血条"用全屏后处理多一条 pass，用 DOM 遮罩又吃不掉颜色；MVP 不定型就要返工。
  2. 光锥是大面积加法混合透明体，叠上 1008 个发光观众，overdraw 可能先于几何成为瓶颈；DPR 按 2 等于四倍像素。
  3. 八个系统（4 座区 × 4 噪音 × 3 线 × Boss 3 阶段 × 静默 × 终曲 × 空场 × 安可）需要单一 owner，否则 dev-three 与 dev-audio 互相等。
- 三个必须回答的问题：
  1. 血条视觉现在定哪一个（后处理 / DOM 遮罩 / 顶点色）？M4 才定就无法进验收矩阵。
  2. 1008 个 instanceColor 能否只更新脏区？请给每帧预算（sim ≤4ms、render ≤6ms）。
  3. 90 秒门由谁、在哪个构建上测？工程需先交"无提示 + 一束光 + 两排人"的最小构建。
- Verdict：advance　｜　风险等级：medium
- 收敛路径：8 卡→5；四座区→先 2 区 + 声部映射；3 线→1 线；Boss 3→2；安可 1 次；静默 8 小节→4 小节。顺序：座位网格与灯光先做，再上人浪、唱化、终曲。

## 交叉比较

- **差异是否真实、是否换皮？** 真实。数据结构不共享：A 是 16 步表 + 二维密度场；B 是六根变形弦 + 音高映射；C 是座位网格 + 光遮罩 + 声部池。共享的只有引擎、输入、相机、实例化人群、音频总线与 React 外壳。
- **谁最适合 7 人 + 纯前端栈？** A 最低、C 居中、B 最高；但按新权重这只落在 Feasibility + Scope 的 10% 上，不该成为选案理由。
- **谁最容易"截图就有人想玩"？** C（座位 + 人浪 + 光锥）；B 次之；A 最弱，它的名场面是 GIF 而非截图。
- **共享内核**：三案约一半实现量是同一套基础设施，无论选谁都能先开工。

## 总推荐与红线

- 推荐排序（按新权重下的潜力，不是打分）：**C > B > A**。C 押 Fun 30%，B 押 Theme/Originality 40%，A 的稳健只值 10%。
- 可行性判断：三案都有可信路径，**无否决**；B 有两条独立技术路（见文末）。
- 硬约束红线（与难度无关）：
  1. 需要外部音频、字体、贴图或模型的实现；零素材是硬约束。
  2. `file://` 下单文件不可用的特性（AudioWorklet、Worker、动态 import）没有内联或降级路径，且未实测。
  3. 每帧 React setState；每帧 1000+ 实例颜色全量上传且无预算。
  4. 阴影默认开、后处理链进 MVP、真 SpotLight 超过 2 盏。
  5. 无低画质档、无实体硬上限、无 60fps 实测却要过 M5 门。
- 给打分员的提醒：不要用"系统多"当不可行、"范围小"当没深度；Feasibility 只问有没有路。模板写"6 人"、`production-plan` §1.4 写 7 名工程师，请先统一口径。

## 按新权重复核（2026-10-28 用户新指令）

- **权重已变**：Fun 30 / Theme 20 / Originality 20 / Depth 10 / Polish 10 / Feasibility 5 / Scope 5；**取消可行性否决**。
- **修正**：初稿曾按可行性优先给 B 判 hold + 条件否决、排序 A > C > B。现撤回：B 改 **advance**，high 只用于排期与切片顺序；"实现难、内容多"不再是扣分项。
- **修正排序**：**C > B > A**（A 的优势只剩 Feasibility 5% + Scope 5%）；不是替打分员打分。
- **最有野心方案（B）的实现思路**——有确定路，只是要提前压测：
  1. **音色主路径避开 worklet**：启动时用 JS 跑 Karplus-Strong，6 弦 × 2 基准音高共 12 个缓冲区（约 3MB），走 AudioBufferSourceNode；跨品格用 playbackRate 覆盖 ±3.5 半音。
  2. **第二路径再上 worklet**：源码字符串内联、Blob + createObjectURL，M5 第一周实测；不通就回主路径。
  3. **"31 个音同一帧"不等于 31 个合成器**：同一根弦同一音符，用 31 个带 ±15 cent detune 与声像展开的 source 同帧触发；情绪靠变色、震屏、白闪完成。
  4. **六弦用 shader 顶点位移**：`onBeforeCompile` 注入"玩家位置 + 张力 + 撞击"三个 uniform，CPU 只做弦上参数与人潮碰撞。
  5. **千人合唱**：8 声部池 + 程序化 IR 卷积 + 压缩器；人越多只调声部数、失谐与声像。
- **结论**：B 的难点是音色与手感的质量门，不是可行性；不过门就换实现或换冠军。
