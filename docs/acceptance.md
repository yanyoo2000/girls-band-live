## 0. 使用方式

1. **每一项都必须可判定**：通过线是数字或可复述的事实，不接受“感觉可以”。
2. **证据三选一**：命令与真实输出、报告文件路径（`docs/qa/*.md`）、截图/录像路径（`docs/qa/shots/`）。没有证据的项按“未验证”处理，视为未通过。
3. **优先级**：`P0` = M6 门禁必须全过；`P1` = 不阻塞发布，但必须在发布说明中列出未完成。
4. **失败处理**：任一 P0 失败 → M6 门禁不通过；不得以“做不完/太难”降级，只能按 `docs/tech-spec.md` §16 的降级路线修，或由制作人书面豁免并记入发布说明。
5. **执行者缩写**：ENG=开发组、UI=dev-ui、THREE=dev-three、AUD=dev-audio、QA=qa-automation、PLAY=qa-playtester、COMPAT=qa-compat、REV=code-reviewer、TD=tech-director。
6. **命令契约**（不可改名）：`npm run typecheck` / `npm test` / `npm run build` / `npm run validate`。
7. **热度口径（全文统一）**：共 5 档 0–4——0 灰 / 1 抬头 / 2 举棒 / 3 合唱 / 4 和声。常态上限为 3；第 5 档 4 仅由「热度上限」卡（`heat-cap`）解锁，HUD 用主色高亮 + 每拍双闪 + 外环表示，输出 +25%、褪色 ×1.5，不新增颜色。实现以 `HeatLevel = 0|1|2|3|4` 与 `heatCapFor()` 为准（与 GDD §4 / §7.3 / §12.2 一致）。

## 5. 特殊判定与豁免

| 情形 | 判定 |
| --- | --- |
| 自动化测试通过但人测未过 | 以人测为准（玩法成立性只能由人验）；不得用单测替代 |
| 人测样本不足 | 记“证据不足”，按未通过处理，除非制作人书面豁免并写明理由 |
| 性能只在高配机达标 | 记录机器型号与 GPU；M6 前必须在 1280×720 的集显/中端机上复测一次 |
| 浏览器差异（Safari） | 仅尽力兼容；不阻塞发布，但不得崩溃白屏 |
| 触屏/移动端相关缺陷 | 不在验收范围（项目决策 0004），不修、不记缺陷 |
| 单文件体积超 4MB | 先按 tech-spec §10.4 裁剪依赖/压缩；仍超则 M6 不通过（需用户确认后才可放宽） |
