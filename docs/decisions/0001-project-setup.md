# 决策记录 0001：项目启动与发布策略

- 日期：2026-10-27
- 状态：已采纳
- 决策人：制作人（captain）

## 背景

用户要求组建一支“非常庞大的智能体团队”，模拟真实游戏公司，完成一款少女乐队主题的吸血鬼幸存者玩法游戏；技术栈限定为简单 HTML；要求从策划到上线每一步都有里程碑、commit、代码/文件提交，并交付成品。本机已安装并登录 GitHub CLI（账号 `yanyoo2000`，repo scope），Node 24 与 Chrome DevTools 可用。

## 决策

1. **仓库**：在当前工作区初始化 Git，创建私有仓库 `yanyoo2000/girls-band-live`，默认分支 `main`。
2. **技术栈**：原生 HTML/CSS/JavaScript；经典脚本 + Canvas 2D + WebAudio；零第三方依赖；构建为单文件 `dist/girls-band-live.html`，`file://` 可玩。
3. **团队**：35 名成员，按管理层 4、策划 10、评审 3、打分 7、开发 6、QA 3、审查/发行 2 配置；共 56 个任务，分 7 个里程碑。
4. **创意流程**：10 份独立 pitch → 10 份交叉互评 → 创意总监融合 3 案 → 3 位评审 → 7 位独立打分 → 制作人中位数计票定案。评分规则见 `docs/brief.md`。
5. **质量流程**：设计定稿 → 实现 → 验证 → 独立代码审查 → 发布集成 → 最终验收；审查不通过必须修复后复审。
6. **提交策略**：成员不执行 Git；制作人在每个里程碑门禁统一 commit/push/tag，并关闭对应 GitHub Milestone/Issue。
7. **发布策略**：开发期仓库保持私有；M7 生成 GitHub Release `v1.0.0` 并附单文件成品。**GitHub Pages 公开上线需用户明确确认**，确认后才切换仓库可见性并开启 Pages。
8. **原创策略**：不使用任何现实乐队、歌曲、艺人形象、动漫角色或第三方素材；音乐与美术全部程序化/原创。

## 后果

- 成本：35 个成员会话 + 56 个任务，运行时间与 token 消耗显著；通过严格 DAG 与并行降低墙钟时间。
- 风险：成员间接口漂移由技术方案与候选版集成兜底；文件冲突由 inScope 与制作人统一提交兜底。
- 退出条件：M7 最终验收通过，`v1.0.0` 可离线试玩，文档/里程碑/提交齐全。

## 备选方案与否决理由

- 使用 React/Vite：违背“简单 HTML”要求，增加依赖与构建复杂度，否决。
- 只做一份企划直接开发：不满足“10 位策划互相讨论、评审、打分”的组织要求，否决。
- 由 captain 直接实现全部代码：无法体现团队协作与质量门，否决。
- 公开仓库开发：未经用户确认不宜公开，改为私有开发 + 发布前确认。
