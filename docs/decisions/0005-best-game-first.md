# 决策记录 0005：最佳游戏优先，技术与工作量不设限

- 日期：2026-10-28
- 状态：已采纳
- 决策人：用户

## 背景

用户明确指示：**技术和工作量不是问题，一切只追求最好的游戏**。对 AI 工程团队而言，不存在“工作量太大”或“技术太难”作为降低创意的理由。此前 M3 rubric 中 Feasibility 20% + Scope 10% 会系统性惩罚大胆方案，与这一目标冲突。

## 决策

1. **调整评审权重**：玩法乐趣 30%、主题表达 20%、原创性 20%、深度与重玩 10%、完成度潜力 10%、技术可实现性 5%、范围控制 5%。
2. **取消可行性否决**：除非方案违反离线/桌面/原创/单文件等硬约束，否则不得以“实现难”否决。
3. **Feasibility 重新定义**：只判断是否存在可信的桌面浏览器 + Three.js + WebAudio 实现路径，不判断难度；Scope 只判断能否完整收口，不因野心大扣分。
4. **GDD 取舍原则**：在保证完整可交付的前提下，优先保留更有野心的内容规模与体验；不得为“省工作量”砍掉乐趣/主题核心。技术总监必须为选中方案设计实现路径，而不是要求创意降级。
5. **质量门不变**：最终仍必须通过 typecheck / test / build / validate、代码审查、实机试玩与验收；野心不能成为半成品的借口。

## 后果

- M3 打分员与评审必须按新权重复核；旧任务描述中的 25/15/20/10/10/10/10 作废。
- M4 GDD 将更倾向于保留冠军方案的完整内容，而不是先砍到“安全范围”。
- 技术方案的难点从“能不能做”转为“怎么在硬约束内做到最好”；集成、性能与完成度仍然是硬门。
- 若最终发现某个设想在浏览器内确实不可实现，技术总监必须提出等价替代，而不是直接删除体验。
