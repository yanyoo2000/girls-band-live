# 项目简报 / Creative & Product Brief

- **项目代号**：Girls Band Live（工作名；最终游戏名在 M3 定案，仓库名不变）
- **版本**：1.0
- **日期**：2026-10-27
- **适用对象**：全体工作室成员（策划、评审、打分员、工程师、QA、发行）

---

## 0. 一页速览

我们要做一款 **少女乐队题材的吸血鬼幸存者（horde survival）**：10 分钟一局，角色自动攻击，玩家在怪潮中走位、吃经验、升级三选一、把乐器武器进化，最后在 Livehouse 的灯光下击败“静默制作人”。

它必须同时满足三件事：

1. **像一款真正的幸存者游戏**：怪潮密度、构筑成长、局内节奏、重开欲望。
2. **像一支真正的少女乐队**：角色有性格与关系，乐器即武器，音乐即战斗反馈。
3. **真的能玩**：原生 HTML，离线单文件，键盘/触屏均可，无报错，60fps 目标。

---

## 1. 产品定义

| 项 | 定义 |
| --- | --- |
| 类型 | 自动攻击 + 怪潮生存 + 局内构筑（Vampire Survivors-like） |
| 主题 | 少女乐队：排练室、Livehouse、巡演、粉丝、成员羁绊 |
| 平台 | 桌面浏览器优先（Chrome/Edge/Firefox），移动浏览器可玩 |
| 单局时长 | 目标 10 分钟；Boss 在 9:00 登场，击败 Boss 即胜利；12:00 强制结算 |
| 操作 | 移动（WASD/方向键/虚拟摇杆）+ 自动攻击 + 1 个主动技「Encore」（Space/按钮）+ 暂停 |
| 情绪基调 | 明亮、热血、青春、略带中二；不猎奇、不黑暗、不卖惨 |
| 目标玩家 | 二次元/乐队题材受众、幸存者类玩家、10 分钟碎片时间玩家、移动端玩家 |
| 参考坐标 | 玩法结构参考 Vampire Survivors；气质参考乐队青春题材。**只参考类型与情绪，不复制任何角色、美术、音频、文案、UI。** |

### 一句话卖点

> 把 Livehouse 变成战场：你的吉他、贝斯、鼓点和歌声就是武器，噪音怪物从台下涌来，用一场 10 分钟的演出守住舞台。

## 2. 设计支柱（所有方案必须通过）

1. **音乐即玩法**：节拍、音强、乐器音色必须影响战斗反馈（攻击节奏、波次强度、Boss 阶段、UI 脉动），而不是只做背景音乐。
2. **3 分钟懂，10 分钟爽**：第一次玩 3 分钟内理解移动/自动攻击/升级；一局结束前至少体验到一次“构筑成型”的高光。
3. **角色是乐队成员，不是换皮职业**：三名成员有各自的性格、乐器、战斗语言与台词；角色差异要能被玩家一句话说出来。
4. **轻量、原创、可传播**：零依赖、离线、单文件、原创 IP；截图/短视频能一眼看出“少女乐队 + 幸存者”。
5. **尊重玩家时间**：暂停可靠、失败不惩罚过重、重开成本低、无强制等待。

## 3. P0 内容基线（不可缩水）

| 模块 | P0 要求 |
| --- | --- |
| 角色 | 3 名可玩乐队成员，各有独立基础攻击、被动、Encore 大招、台词与配色 |
| 武器 | 6 把乐器/演出武器；每把 5 级；每把有 1 个进化形态（需满级 + 指定被动） |
| 装备位 | 最多 4 武器 + 4 被动；升级三选一；卡池受槽位与进化条件约束 |
| 敌人 | 8 种普通/精英“噪音”怪物 + 1 个多阶段 Boss |
| 关卡 | 1 张 Livehouse 舞台，至少 3 个视觉/波次阶段（开场、升温、高潮） |
| 局内系统 | 经验、等级、HP、无敌帧、拾取磁吸、击杀数、计时、暂停、结算 |
| 元系统 | localStorage 保存设置与最佳记录；角色/武器解锁为 P1 |
| UI | 主菜单、角色选择、玩法说明、HUD、升级、暂停、设置、结算、制作名单 |
| 音频 | WebAudio 程序化音乐（至少 4 层：鼓、贝斯、和弦、主旋律）+ 关键音效；静音/音量可调 |
| 输入 | 键盘全流程可玩；移动端虚拟摇杆 + Encore 按钮；窗口失焦自动暂停 |
| 无障碍 | 减少动态开关、高对比、键盘焦点可见、无 >3Hz 闪烁、文字可读 |
| 教程 | 首次进入的一页式说明 + 局内提示（不强制长教程） |

> P1（可做但不阻塞发布）：角色/武器解锁、额外舞台换色、每日挑战种子、成绩分享图、更多台词。
> P2（不做）：联机、账号、内购、关卡编辑器、完整多语言、3D、外部素材、版权音乐。

## 4. 技术与交付硬约束

1. **原生 HTML/CSS/JavaScript**，零第三方运行时依赖，零 npm 依赖，零网络请求。
2. **单文件成品**：`dist/girls-band-live.html` ≤ 2MB（目标 ≤ 1MB），`file://` 双击可玩。
3. 不允许外部字体、图片、音频、CDN、埋点、远程接口；所有视觉用 Canvas/CSS/SVG，所有声音用 WebAudio 合成。
4. 经典脚本（非 ES module）按固定顺序加载；每个模块挂 `window.GBL`，纯逻辑模块在 Node 下可 `require` 以便测试。
5. 逻辑分辨率 1280×720，按窗口等比缩放；移动端 390×844 竖屏可用（可提示横屏，但不能阻止游玩）。
6. 目标 60fps（150 敌人、中端桌面）；实体硬上限 250；低帧率时允许降级特效，但不允许崩溃。
7. 浏览器：Chrome/Edge 最新两个大版本、Firefox 最新两个大版本；Safari 16+ 尽力兼容；移动 Chrome/Safari 最新版。
8. 存档只允许 localStorage，key 为 `gbl.save.v1`，读取失败必须回退默认值且不阻塞启动。
9. 代码必须通过 `node --check`、`node --test tests`、`node tools/build.mjs`、`node tools/validate.mjs`。
10. 中文字体使用系统字体栈；界面文案中文；代码标识符英文。

## 5. 创意评审 Rubric（1–10 分）

| 维度 | 权重 | 评审问题 |
| --- | ---: | --- |
| 玩法乐趣 Fun | 25% | 核心循环是否立刻好玩？10 分钟是否有节奏起伏与高光？ |
| 主题表达 Theme | 15% | 少女乐队是否长在玩法里，而不是贴皮？角色/音乐/舞台是否有记忆点？ |
| 工程可行性 Feasibility | 20% | 以 P0 范围、6 名工程师、纯 HTML 技术栈，能否在里程碑内稳定交付？ |
| 原创性 Originality | 10% | 是否提供了幸存者品类里没见过的组合或表达？是否规避了抄袭？ |
| 范围控制 Scope | 10% | 是否能在不膨胀的前提下做出完成度？砍掉的都是对的吗？ |
| 深度与重玩 Depth | 10% | 构筑是否有选择空间？角色/武器组合是否值得再开一局？ |
| 完成度潜力 Polish | 10% | 美术、音频、打击感、UI 是否有明确的低成本高回报路径？ |

- 每项 1–10 分，加权总分保留 1 位小数，满分 10.0。
- 7 位打分员独立打分；制作人按**每个维度的中位数**汇总，计算加权总分。
- **可行性否决**：若可行性评审给出“高风险”且可行性中位数 < 6，该方案不能夺冠。
- **乐趣底线**：冠军的乐趣中位数应 ≥ 7；若全部方案低于 7，则加权总分最高者夺冠，但创意总监必须在 GDD 前提交一页「乐趣抢救补丁」。
- **平局**：依次比较 乐趣中位数 → 可行性中位数 → 原创性中位数。
- 打分员不得阅读其他打分员的文件；评审意见可以阅读。

## 6. 完成定义（Definition of Done）

一个版本只有在以下全部成立时才算完成：

1. `dist/girls-band-live.html` 可离线打开，控制台无未处理错误，无外部网络请求。
2. 从主菜单到角色选择、完整一局、Boss、结算、重开，全流程可玩；暂停/继续/设置/静音可靠。
3. 3 角色、6 武器、6 进化、8 敌人、1 Boss、1 舞台全部可达；无占位内容。
4. P0 验收矩阵 100% 通过；P1 未完成项在发布说明中明确列出。
5. `node --test tests` 全绿；`node tools/build.mjs` 与 `node tools/validate.mjs` 通过。
6. 独立代码审查 verdict = pass；无 blocker/high 级问题。
7. README、CHANGELOG、发布说明、制作名单完整；GitHub Milestone/commit/tag/release 齐全。
8. 桌面 1920×1080 与移动 390×844 各完成一次 QA 实机试玩并留存证据。

## 7. 非目标（明确不做）

- 不复制或影射任何现实乐队、歌曲、歌词、艺人形象、动漫角色、商标。
- 不做联机、排行榜服务器、账号体系、内购、广告、数据采集。
- 不做关卡编辑器、模组系统、多语言、配音、3D、过场动画。
- 不引入任何 npm 包、框架、构建器、CSS 框架、图标库、音频素材包。
- 不为“以后可能用得上”预留复杂度；不为 P2 写代码。

---

## 8. 原创与合规

- 角色名、乐队名、曲名、歌词、怪物名、UI 文案必须原创；如与现有作品撞名，改名。
- 音乐必须是程序化合成或原创旋律，不得复刻已知歌曲的和声进行/旋律。
- 禁止使用或模仿具体艺人的肖像、声线、标志性造型。
- 所有代码与文档默认归本项目仓库所有；发布前由发行经理复核第三方素材为零。

---

## 9. 给策划与评审的提醒

- 好点子不是“元素清单”，而是**一个能被 30 秒讲清楚的动词**：你在舞台上做什么、为什么停不下来。
- 每个方案必须回答：为什么必须是少女乐队？换成任何其他题材还成立吗？如果成立，方案不合格。
- 每个方案必须自带“减法”：为了 10 分钟一局，你砍掉了什么？
- 允许大胆，但必须可交付；P0 基线是地板，不是天花板。
- 评价方案时，先评价它想成为什么，再评价它现在写了什么。
