# 项目简报 / Creative & Product Brief

- **项目代号**：Girls Band Live（工作名；最终游戏名在 M3 定案）
- **版本**：2.0（2026-10-28 创意自由修订）
- **适用对象**：全体工作室成员

---

## 0. 一页速览

我们要做一款 **少女乐队题材的吸血鬼幸存者（horde survival）**：短局、自动攻击、怪潮、成长构筑，在 Livehouse 的灯光与噪音里完成一场演出。

它必须同时满足三件事：

1. **像一款真正的幸存者游戏**：怪潮密度、构筑成长、局内节奏、重开欲望。
2. **像一支真正的少女乐队**：角色有性格与关系，乐器即武器，音乐即战斗反馈。
3. **真的能玩**：React + TypeScript + Three.js，桌面浏览器，离线单文件，无报错。

**最重要的目标：让玩家在几分钟内遇到一个此前没见过的时刻，并愿意讲给别人听。**

## 1. 产品定义

| 项 | 定义 |
| --- | --- |
| 类型 | 自动攻击 + 怪潮生存 + 局内构筑（Vampire Survivors-like），允许融合其他类型 |
| 主题 | 少女乐队：排练室、Livehouse、巡演、粉丝、成员羁绊 |
| 平台 | 仅桌面浏览器（Chrome/Edge/Firefox，WebGL2）；不做移动端/触屏 |
| 单局时长 | 由 GDD 决定，目标 5–20 分钟；必须在一局内完成一次完整的成长/情绪弧 |
| 操作 | 键盘移动 + 鼠标菜单 + 自动攻击 + 至多 1 个主动技 + 暂停；不做触屏 |
| 情绪基调 | 明亮、热血、青春、略带中二；不猎奇、不黑暗、不卖惨 |
| 目标玩家 | 二次元/乐队题材受众、幸存者类玩家、短局桌面玩家 |
| 参考坐标 | 玩法结构参考 Vampire Survivors；气质参考乐队青春题材。只参考类型与情绪，不复制任何角色、美术、音频、文案、UI。 |

### 一句话卖点

> 把 Livehouse 变成战场：你的乐器、歌声和舞台就是武器，噪音从台下涌来，用一场演出守住舞台。

## 2. 设计支柱

1. **音乐即玩法**：节拍、音强、乐器音色必须影响战斗反馈，而不是只做背景音乐。
2. **几分钟懂，一局内爽**：第一次玩能快速理解；一局结束前至少体验到一次“构筑成型/情绪爆发”的高光。
3. **角色是乐队成员，不是换皮职业**：成员有性格、乐器、战斗语言与台词；差异要能被玩家一句话说出来。
4. **原创、轻量、可传播**：离线、单文件、原创 IP；截图/短视频能一眼看出“少女乐队 + 幸存者”。
5. **尊重玩家时间**：暂停可靠、失败不惩罚过重、重开成本低、无强制等待。

### 2.1 M1 创意自由原则（2026-10-28 修订）

- M1 是创意探索，不是需求文档：**不设模板、不设字数、不要求凑任何内容数量**。
- 每位策划先写让自己兴奋、让玩家惊艳的东西；可以颠覆类型惯例、混合叙事/音游/表演/空间玩法，允许暂时“不可交付”。
- **唯一硬约束**：原创、围绕“少女乐队 × 幸存者”、最终能收敛成桌面 React + TypeScript + Three.js 的可玩版本。
- 角色数量、武器数量、敌人数量、Boss 形态、单局时长、关卡数量、音乐层数等，全部**不预设**；M3 定案与 M4 GDD 再锁定。
- 可行性、范围与减法留到 M2/M3/M4；评审会区分“大胆且有根”与“空洞堆料”。
- **技术与工作量不是创意的边界**：AI 工程团队可以承担复杂实现；不要因为“太难/内容太多”而自我阉割。唯一要求是最终能完整交付、可玩、可验收。
- 旧版 12 节模板与详细企划已归档，只作历史，不参与本轮评审。

## 3. 生产底线（功能，不是数量）

**不预设内容数量**。最终角色、武器、敌人、Boss、关卡、单局时长的规模，由 M3 冠军方案与 M4 GDD 锁定。在保证完整可交付的前提下，**优先选择更有野心的内容规模**：技术/工作量不是限制，唯一约束是最终能完整收口、可玩、可验收。以下只是“必须成立的功能”，不是清单：

- **完整单局**：开始 → 成长 → 高潮 → 结束 → 结算 → 重开，全流程可玩。
- **可操作主体**：至少 1 名可玩的乐队成员；如果做多角色，必须有可感知的差异。
- **核心战斗与成长**：至少 1 套自动攻击/技能与至少 1 条局内成长/选择路径。
- **威胁与高潮**：可辨识的敌人/威胁体系，以及至少 1 个高潮事件（Boss、演出事故、终曲、停电等，形式由设计决定）。
- **舞台/场景**：至少 1 张可辨识的 Livehouse 舞台或等价场景；可有多阶段。
- **UI 流程**：主菜单、玩法说明、HUD、成长/升级选择、暂停、设置、结算、制作名单；选人界面按是否多角色决定。
- **存档**：设置与最佳记录（推荐；如设计不需要可省略，但需在 GDD 说明）。
- **音频**：音乐 + 关键 SFX；层数与数量由设计决定，但必须真的参与体验。
- **桌面操作**：键盘全流程 + 鼠标菜单；不做触屏/移动端。
- **质量底线**：原创、离线单文件、无外部素材、无未处理报错、60fps 目标（可降级）。
- **GDD 必须锁定最终数量**：M4 的验收矩阵以 GDD 锁定的内容为准，不再回看本节的“数量”。

> P1/P2 由 GDD 根据冠军方案决定；默认原则：不做联机、账号、内购、关卡编辑器、完整多语言、配音、过场动画、移动端。

## 4. 技术与交付硬约束

1. **React + TypeScript + Three.js**：React 19 管理所有 DOM UI，Three.js 0.186 负责 3D 舞台与战斗渲染，Vite 8 负责开发与构建。
2. **TypeScript strict**：`npm run typecheck`（`tsc --noEmit`）必须 0 错误；禁止无理由的 `any`；共享类型集中在 `src/types/`。
3. **依赖策略**：默认保持最小依赖；允许按项目需要引入外部库/框架，但必须由技术总监评估并记录在 `docs/tech-spec.md` 的依赖清单与 `docs/decisions/` 中。评估维度：必要性、包体、许可证、维护状态、离线可用性、供应链风险。新增依赖必须锁定版本并提交 `package-lock.json`；禁止 CDN 运行时依赖、需要联网服务的库与包含版权素材的包。
4. **单文件成品**：`npm run build` 产出 `dist/girls-band-live.html` 与根 `index.html`，≤ 4MB（目标 ≤ 2MB），`file://` 双击可玩；Vite 的常规 `dist/` 产物同时保留。
5. 不允许外部字体、图片、音频、glTF/GLB 模型、CDN、埋点、远程接口；所有视觉用 Three.js 基础几何体 + 程序化材质/CanvasTexture + CSS/SVG，所有声音用 WebAudio 合成。
6. **3D 规格**：俯视 3/4 透视相机跟随玩家；低多边形风格；舞台边界与观众区；灯光/霓虹参与玩法反馈；阴影默认关闭，低画质模式可降 DPR 与粒子上限。
7. **性能**：目标 60fps（中端桌面、1280×720 起）；实体硬上限由技术方案决定；敌人/子弹使用 InstancedMesh 或对象池；React HUD 以 ≤10Hz 的快照更新，禁止每帧 `setState`。
8. **浏览器**：仅桌面 Chrome/Edge 最新两个大版本、Firefox 最新两个大版本；要求 WebGL2；Safari 17+ 桌面版尽力兼容；不做移动端/触屏适配。窗口在 1280×720 及以上可用，缩放时画布等比适配。
9. 存档只允许 localStorage，key 为 `gbl.save.v1`，读取失败必须回退默认值且不阻塞启动。
10. 验收命令：`npm run typecheck`、`npm test`、`npm run build`、`npm run validate` 全部通过；构建产物不得包含外部 URL 或外部 module import。中文字体使用系统字体栈；界面文案中文；代码标识符英文。

## 5. 创意评审 Rubric（1–10 分）

| 维度 | 权重 | 评审问题 |
| --- | ---: | --- |
| 玩法乐趣 Fun | 30% | 核心循环是否立刻好玩？一局内是否有节奏起伏与高光？ |
| 主题表达 Theme | 20% | 少女乐队是否长在玩法里，而不是贴皮？角色/音乐/舞台是否有记忆点？ |
| 原创性 Originality | 20% | 是否提供了幸存者品类里没见过的组合或表达？是否规避了抄袭？ |
| 深度与重玩 Depth | 10% | 构筑/选择/角色是否有重玩空间？ |
| 完成度潜力 Polish | 10% | 美术、音频、打击感、UI 是否有明确的低成本高回报路径？ |
| 技术可实现性 Feasibility | 5% | 是否存在可信的桌面浏览器/Three.js/WebAudio 实现路径？只问“有没有路”，不问“难不难”。 |
| 范围控制 Scope | 5% | 是否能在不牺牲核心体验的前提下完整交付？只问“能不能收口”，不因野心大扣分。 |

- 每项 1–10 分，加权总分保留 1 位小数，满分 10.0。
- 7 位打分员独立打分；制作人按**每个维度的中位数**汇总，计算加权总分。
- **技术与工作量不是扣分项**：AI 工程团队可以承担复杂实现；不得因为“太难/内容太多”降低任何分数。Feasibility 只判断是否存在可信路径，Scope 只判断能否完整收口。
- **取消可行性否决**：除非方案违反离线/桌面/原创/单文件等硬约束，否则不得以“实现难”否决。
- **乐趣底线**：冠军的乐趣中位数应 ≥ 7；若全部方案低于 7，则加权总分最高者夺冠，但创意总监必须在 GDD 前提交一页「乐趣抢救补丁」。
- **平局**：依次比较 乐趣中位数 → 原创性中位数 → 主题中位数。
- 评审不要求方案已经凑齐内容数量；只评估它成为“最好的游戏”的潜力，以及在硬约束内完整交付的路径。

## 6. 完成定义（Definition of Done）

一个版本只有在以下全部成立时才算完成：

1. `dist/girls-band-live.html` 可离线打开，控制台无未处理错误，无外部网络请求。
2. 从主菜单到完整一局、高潮事件、结算、重开，全流程可玩；暂停/继续/设置/静音可靠。
3. **GDD 锁定的 P0 内容全部可达**；无占位内容；未完成项在发布说明中明确列出。
4. P0 验收矩阵 100% 通过。
5. `npm run typecheck` 与 `npm test` 全绿；`npm run build` 与 `npm run validate` 通过。
6. 独立代码审查 verdict = pass；无 blocker/high 级问题。
7. README、CHANGELOG、发布说明、制作名单完整；GitHub Milestone/commit/tag/release 齐全。
8. 桌面 1920×1080 与 1366×768 各完成一次 QA 实机试玩并留存证据；不做移动端/触屏验收。

## 7. 非目标（明确不做）

- 不复制或影射任何现实乐队、歌曲、歌词、艺人形象、动漫角色、商标。
- 不做联机、排行榜服务器、账号体系、内购、广告、数据采集。
- 不做移动端/触屏适配；游戏只面向桌面浏览器。
- 不做关卡编辑器、模组系统、多语言、配音、过场动画。
- 不预设依赖黑名单；可以按需引入经过技术总监评估、版本锁定、记录在案的库/框架。
- 禁止：未经评估的依赖、CDN 运行时依赖、需要联网服务的库、包含版权素材的素材包。
- 不为“以后可能用得上”预留复杂度。

---

## 8. 原创与合规

- 角色名、乐队名、曲名、歌词、怪物名、UI 文案必须原创；如与现有作品撞名，改名。
- 音乐必须是程序化合成或原创旋律，不得复刻已知歌曲的和声进行/旋律。
- 禁止使用或模仿具体艺人的肖像、声线、标志性造型。
- 所有代码与文档默认归本项目仓库所有；发布前由发行经理复核第三方素材为零。

---

## 9. 给策划与评审的提醒

- **M1 先别自我审查**：不要为了“能不能做完”砍掉想象力；先写出让你自己兴奋的东西。
- 好点子不是“元素清单”，而是**一个能被 30 秒讲清楚的动词**：玩家在舞台上做什么、为什么停不下来。
- 评审会追问：为什么必须是少女乐队？换成别的题材还成立吗？这不是填表项，而是判断原创性的问题。
- 减法留到 M3 定案：那时再一起决定为了短局砍掉什么。
- 允许大胆，甚至允许暂时不可交付；M2/M3 会评估如何收敛。
- 评价方案时，先评价它想成为什么，再评价它现在写了什么。
